const routes = {
    "GET /":            getHome,
    "GET /health":      getHealth,
    "GET /users/:id":   getUser,
    "POST /echo":       postEcho,
};

function handler(req) {
    const match = routerMatch(routes, req);
    if (match) {
        req.params = match.params;
        return match.handler(req);

import { parseBearer, jwtVerify } from "zigttp:auth";
import { schemaCompile, validateJson } from "zigttp:validate";

schemaCompile("user", JSON.stringify({
    type: "object",
    required: ["name", "email"],
    properties: {
        name:  { type: "string", minLength: 1 },
        email: { type: "string", minLength: 5 },
    }

function handler(req) {
    const token = parseBearer(req.headers["authorization"]);
    if (!token) return Response.json(
        { error: "unauthorized" }, { status: 401 }
    );

    const auth = jwtVerify(token, "my-secret");
    if (!auth.ok) return Response.json(
        { error: auth.error }, { status: 401 }
    );

    if (req.method === "POST") {
        const result = validateJson("user", req.body);
        if (!result.ok) return Response.json(
            { errors: result.errors }, { status: 400 }
        );
        return Response.json({ user: result.value }, { status: 201 });
    }

    return Response.json({ user: auth.value });
}

PROOF LEVEL: complete

Not a V8 wrapper. Not a QuickJS fork. Built from zero.

zts is a TypeScript engine with one job: run a request handler as fast as possible, prove it correct, and get out of the way. Purpose-built in Zig, start to finish.

Two-pass compilation

Parse to IR, then bytecode. The IR tree is the single source of truth for 7 verification passes, data flow analysis, contract extraction, and path enumeration. One parse, many proofs.

NaN-boxing with hidden classes

Type-prefix NaN-boxing: one shift-and-compare per type check. V8-style hidden class transitions with 8-entry polymorphic inline cache. Shape preallocation for HTTP objects - zero transitions on the hot path.

Hybrid arena allocation

Request-scoped arena with O(1) alloc and O(1) bulk reset. Write barriers detect arena escape. GC disabled in hybrid mode. 4MB per request, freed in a single pointer reset.

Baseline + optimized JIT

x86-64 and ARM64. Baseline JIT after 100 calls with inline cache fast paths. Optimized tier with hoisted guards, unboxed arithmetic, and register allocation. Type-directed codegen from BoolChecker proofs.

comptime(): Zig's best idea, now in TypeScript.

Evaluate expressions at load time, not request time. The result is baked into bytecode as a constant. Zero per-request cost. Inspired by Zig's comptime - brought to TypeScript for the first time.

handler.ts 
// Evaluated once at load time, not per request
const VERSION_HASH = comptime(hash("v2.1.0"));
const MAX_BODY    = comptime(1024 * 1024 * 10);
const GOLDEN      = comptime((1 + Math.sqrt(5)) / 2);
const HEADER      = comptime("x-api-version".toUpperCase());

// Schema compiled once, validated every request
comptime(schemaCompile("user", JSON.stringify({
    type: "object",
    required: ["name", "email"],
    properties: {
        name:  { type: "string", minLength: 1 },
        email: { type: "string", format: "email" }
    }
})));

const handler = (req: Request): Response => {
    // VERSION_HASH, MAX_BODY, GOLDEN, HEADER are all constants here
    // No computation, just bytecode literals
    const result = validateJson("user", req.body);
    if (!result.ok) return Response.json({ errors: result.errors }, { status: 400 });
    return Response.json({ created: true, user: result.value }, { status: 201 });
};

What runs at load time

Arithmetic, Math methods, string methods, parseInt/parseFloat, JSON.parse, hash(), and schemaCompile(). Pure, deterministic expressions only - no I/O, no side effects.

What you get at request time

A bytecode constant. The expression is gone - replaced by its result. Your handler pays zero cost for values that never change between requests.

Why this matters for FaaS

Serverless handlers run millions of times. A schema compiled once at load time instead of per-request eliminates microseconds that compound into real money on your Lambda bill.

What is zigttp?

zigttp is a TypeScript runtime built from scratch in Zig, designed specifically for serverless and FaaS workloads. It compiles your handler into a single binary with zero dependencies, achieving 3ms cold starts, a 1.2MB binary size, and 80K requests per second throughput.

How is zigttp different from Node.js, Deno, and Bun?

Node.js, Deno, and Bun are general-purpose runtimes that support the full language specification. zigttp takes the opposite approach: it implements an opinionated TypeScript subset that removes footgun features (classes, this, exceptions) at parse time and replaces async/await with sync-looking code backed by Zig's async I/O. This constraint enables compile-time verification of handler correctness, automatic least-privilege sandboxing, durable execution, and deterministic replay - none of which are possible when the runtime must support arbitrary TypeScript. If you need a general-purpose runtime, use Node.js, Deno, or Bun. If you want provably correct serverless handlers with minimal cold starts, zigttp is the better fit.

What TypeScript features does zigttp support?

zigttp supports arrow functions, const/let, destructuring, template literals, for...of, optional chaining, nullish coalescing, the pipe operator, array methods (map, filter, reduce), JSX/TSX, TypeScript type stripping, and comptime() evaluation. Features like classes, var, while loops, and try/catch are intentionally excluded with parse-time errors that suggest alternatives. async/await is replaced by sync-looking code backed by Zig's async I/O - use parallel() and race() for concurrency.

How fast is zigttp compared to Node.js, Deno, and Bun?

zigttp runtime initializes in ~3ms vs ~100-130ms for Bun, ~150-200ms for Deno, and ~200-300ms for Node.js. Linux static builds achieve 18-33ms end-to-end cold start. The binary is 1.2MB vs 80-130MB for the others. Memory baseline is 4MB vs 20-30MB. These gains come from Zig's zero-overhead abstractions and a custom TS engine (zts) purpose-built for short-lived request handlers.

Is zigttp free and open source?

Yes. zigttp is MIT licensed and available on GitHub. The entire runtime, compiler, and standard library of virtual modules are open source.

What are virtual modules?

Virtual modules (zigttp:auth, zigttp:cache, zigttp:sql, zigttp:io, etc.) are built-in capabilities implemented in Zig with zero interpretation overhead. They provide JWT authentication, key-value caching, SQLite queries, parallel I/O, durable execution, and more - all accessible through standard import syntax and tracked by the compiler for automatic sandboxing.

Can I use zigttp instead of Bun for serverless functions?

Yes, if your use case is request-response serverless handlers. Bun is a general-purpose runtime that supports the full Node.js API, npm packages, and arbitrary TypeScript. zigttp is purpose-built for FaaS: it trades generality for a 1.2MB binary, 4MB memory footprint, compile-time handler verification, and automatic sandboxing. For serverless workloads where cold start time and resource efficiency matter, zigttp is a strong Bun alternative.

Why is zigttp built in Zig instead of Rust or C++?

Zig provides manual memory control with comptime metaprogramming, no hidden allocations, and no runtime overhead - ideal for building a TypeScript engine where every microsecond of cold start matters. Unlike C++, Zig has no hidden constructors or exceptions. Unlike Rust, Zig avoids borrow checker complexity while still preventing undefined behavior through explicit error handling. Zig's comptime evaluation also powers zigttp's build-time handler verification.

Does zigttp support TypeScript?

Yes. zigttp natively strips TypeScript type annotations at parse time with zero overhead - no transpilation step, no tsc, no build tool. You write TypeScript (or TSX for JSX components) and zigttp handles it directly. The supported subset includes const/let type annotations, function parameter types, return types, interfaces, and generics for type checking.

Can I migrate from Node.js or Express to zigttp?

zigttp is not a drop-in replacement for Node.js. It implements a restricted TypeScript subset and does not support npm packages, the Node.js API, or middleware frameworks like Express - it uses arrow function composition instead. However, if your serverless handlers are stateless request-response functions, the migration path is straightforward: rewrite handlers using zigttp's functional style and virtual modules. The result is a provably correct, single-binary deployment with dramatically lower cold starts.

What does "proves your code correct" mean?

The compiler walks every possible execution path through your handler and checks 7 properties statically. It proves every path returns a Response, every Result is checked before access, no module-scope state leaks between requests, no unvalidated input reaches sensitive sinks, match expressions are exhaustive, and optionals are narrowed before use. These are not type hints or linter rules - they are exhaustive proofs derived from the restricted language subset. The IR tree IS the control flow graph, so verification is a tree walk, not fixpoint iteration.

How does OWASP compliance mapping work?

The compiler maps its proven properties to OWASP Top 10 categories automatically. No secrets leaking to responses proves A01. No credentials in logs proves A02. All input validated before egress proves A03. Contract-derived sandbox proves A05. All Results checked before access proves A07. The deploy report shows PROVEN or --- for each category. These are compiler proofs, not self-declarations.

How do AI coding agents work with zigttp?

zigttp ships with purpose-built agents, skills, and MCP tools for AI-assisted development. The restricted language subset means agents generate valid handlers reliably - 14 supported features instead of 200, one handler pattern instead of dozens, and the compiler verifies everything the agent writes. Custom agents know every virtual module API. Skills scaffold handlers from natural language descriptions. MCP tools let any AI assistant query the language spec and module signatures at code-generation time.

Can I use zigttp in CI/CD pipelines?

Yes. zig build prove -- old.json new.json compares two handler contracts and exits 0 (equivalent or additive change, safe to deploy) or 1 (breaking change, needs review). Use it as a PR gate. zig build mock -- tests.jsonl --port 3001 generates a mock server from compiler-generated test cases for frontend integration testing. Both tools work without rebuilding the handler.
