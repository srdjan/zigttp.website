zttp is an agent-compiler

The agent writes only what the compiler can prove.

One system, three parts built against each other: a restricted TypeScript the compiler can decide, a proof engine total over that language, and a coding agent that authors inside the fence. Every draft is simulated before it touches disk. A draft that adds violations is vetoed. When the agent fails, the compiler writes the fix itself.

Why nothing else can do this

The failure is not the model. It is the boundary.

Every current tool bolts an agent onto a checker, or a checker onto an agent. In the first shape the checker is heuristic and post-hoc. In the second, the compiler is a passive oracle returning error strings into an unbounded search. In both shapes the agent can emit programs the checker cannot judge, because the language admits them.

agent, then checker

The model writes, a linter grades. A linter gives advice about an unbounded language, the model routes around it, and "no findings" proves nothing.

checker, then agent

The compiler is a passive oracle. It returns error strings into an unbounded search and never constrains what the next draft may contain.

agent-compiler

One write path, and the compiler sits on it. The language is closed first, so every program the agent can emit is a program the compiler can judge.

Why the language is restricted

Human languages reward expressiveness: more than one way to do it, style as identity, sugar for every faction. For a model that multiplicity is not a feature. Every extra way to write the same loop widens the search space, and a wider search space is where hallucination lives.

zts closes the space. Each removal below buys a proof, which is why the restrictions are the product rather than a limitation to grow out of. Re-admitting a construct un-ships proofs.

  • while

    No back-edge. The analyzer walks every path of every handler and terminates, so "no findings" is a theorem over the whole handler, not a sample of it.

  • try/catch

    No invisible control-flow edge out of any statement. Failure becomes a Result the compiler can see, so every path still returns.

  • async

    No hidden suspension points. Handler code stays linear, so determinism and replay are decidable and concurrency moves into the I/O layer.

  • class

    No shared mutable receiver. Data flow is explicit, which is what makes state_isolated provable.

  • this

    No binding that changes meaning with the call site. Every reference resolves statically.

  • new

    No constructor-shaped identity. Values stay plain data the analyzer can track through a flow.

  • regex

    No opaque matcher with unbounded backtracking. Input handling stays analyzable, so injection_safe can be a flow proof rather than a convention.

  • ==

    No coercion table between the value and the comparison. Types stay nominal, so boolean checks are enforceable everywhere.

  • null

    One absent value instead of two. Absence becomes a case the match has to cover.

This is not a compiler for agents. It is an agent and a compiler built as one machine.

Inside the fence

The compiler does not check the work. It co-authors it.

The model in zttp expert has exactly one write path, and the compiler sits on it. Every draft is simulated before it touches disk. Nothing lands red.

model lane
  1. Draft

    The agent writes the handler. If the request is materially ambiguous, it asks one question first.

  2. Simulate

    The compiler runs the draft through the full proof pass before it touches disk.

  3. Veto

    A draft that adds violations is refused, and drops to the compiler lane. Veto exhaustion ends the turn: it never ships the draft.

compiler lane: zero model calls
  1. Salvage

    The compiler first tries to save the draft itself: canonicalize the source, then re-simulate.

  2. Plan

    If salvage fails, it composes a typed repair plan. The plan names the property and carries a specific remedy.

  3. Apply

    The edit lands with no model call. The session records it as compiler-authored.

  4. Verify or roll back

    The result is re-proved. A regression rolls the edit back rather than shipping it.

For three safety properties the whole loop runs with no model at all: the compiler plans, applies, verifies, and rolls back on regression. No tokens, no sampling, no drift. Each mechanical repair moves authorship from the model to the compiler.

State of the evidence

Convergence: measured, not claimed.

The design pulls two sets toward each other: the programs the agent can write, and the programs the compiler can prove. One direction holds today by construction, because the agent cannot land a draft the compiler rejects: the veto is on the only write path. The other direction, that the agent can reach everything the compiler can prove, is open. Nothing measures it yet. We measure the gap. We do not claim it is closed.

zttp sells verdicts over vibes. A product that grades your code has to grade its own claims the same way, so here is the current ledger. It is versioned with the repo and it will change before it flatters.

The claim ledger

self-graded

Holds by construction

proven properties of the system itself, true by how it is built

  • single fenced write path

    The compiler sits on the only path a draft can take to disk. There is no second route by which a model edit reaches a file.

  • veto with canonicalize-and-salvage

    A draft that adds violations is refused before it lands. On the veto the compiler canonicalizes the source and re-simulates before anything else runs.

  • model-free repair lane

    A typed repair plan is composed and applied with zero model calls, and the session records the edit as compiler-authored.

  • autoloop rollback on regression

    For three safety properties the compiler plans, applies, verifies, and rolls back with no model in the loop at all.

  • replayable counterexamples

    A failed property yields a real request plus I/O stubs in the same trace format the runtime records, so the witness replays against the production engine with no translation.

  • registry hashes on every agent response

    Each response is bound to the exact rule, idiom, and restriction set in force when it was produced.

Thin today

real, but narrower than the claim deserves

  • wire protocol missing its three agent verbs

    An outside client can ask what is wrong. It cannot yet ask the compiler to simulate, repair, or verify, so on that wire every rewrite grades as a proposed refactor and none is a mechanical repair.

  • most repair intents do not lower to an edit

    Mechanical repair lives only inside the agent package, and only a minority of typed repair intents lower to a real source edit.

  • no canonical formatter

    Every rewrite splices byte spans instead of reprinting from a canonical form.

  • capability ceilings are per module

    Ceilings are declared per module rather than per export, so every ceiling is coarser than the code it describes.

Unmeasured

no honest denominator exists yet, so no number is published

  • first-draft-correct rate

    The share of agent drafts that clear the veto with no retry is the most direct reading of convergence, and it has no honest denominator today.

  • the convergence gap

    Given a reference suite the compiler certifies green, the fraction the agent reproduces to green inside a fixed budget. Nothing measures it today.

  • ledger aggregates

    The session ledger is local, per-workspace, and empty by default, so round-trips to first green proof cannot be stated honestly yet.

  • intent coverage in the eval corpus

    The current corpus checks compiler compliance, not intent. The one agent number ever published is stale, which is why it does not appear on this page.

No number leaves the repo without a versioned eval behind it. That is why this section shows grades, not scores. Every count sits in the roadmap beside the file that owns it, so you can recount it instead of trusting a number that rots on a landing page.

What zttp refuses to build

  • refused
    Full Node and V8 language fidelity

    The permanent non-goal. Full fidelity is what makes these proofs intractable everywhere else.

  • refused
    Any unproven escape hatch

    No mode ships unrestricted code behind a warning label. Veto exhaustion ends the turn; it never ships the draft.

  • refused
    Re-admitting restricted constructs

    Each restriction maps to a proof it unlocks, so re-admitting one under adoption pressure un-ships proofs.

  • refused
    A general-purpose coding agent

    zttp expert does not compete on breadth. It wins inside the fence, and only there.

  • refused
    Learned checkers in the verdict path

    No model-as-judge ever gates a ship. The verdict stays deterministic and total.

  • refused
    Unmeasured or stale numbers

    No number leaves the repo without a versioned eval behind it. That is why this page carries fewer numbers than most.

  • deferred
    A local-model training flywheel

    The narrow grammar is a real reason to think a small model could author inside the fence, but that is a hypothesis with no measurement behind it yet.

Ask this of any tool that checks AI-written code: which of its claims hold by construction, which are thin, and which are unmeasured. A tool that cannot produce this list is asking you to ship on vibes.

Proof carrier

The runtime exists to carry what the compiler proves.

It replays the compiler's counterexamples, runs the proven handler, and ships it as one attested binary. It is also the only part of the system that can falsify the compiler, because witnesses replay against the real engine in the format the compiler wrote them.

one self-contained binary: 4.8 MB public baseline for v0.18.0 7-15 ms cold start, measured in zttp-bench. A floor, never a headline attestation on by default, zttp verify <url> for anyone downstream
Durable workflows show detail
  • Replay safety is a compiler verdict and the runtime is its carrier: it refuses the runs the compiler could not prove. Reusing a completed response needs idempotent; retrying an incomplete run needs retry_safe, or a client Idempotency-Key.
  • Unproven replay fails closed with a soft 599 the client can read, DurableRetryUnproven, never a silent second run.
  • ZTS509 rejects a workflow.call, saga, or fanout inside a durable.step() callback. ZTS510 rejects a static saga missing a compensate on any step but the last.
orchestrator.tsone process, no network 
import { run } from "zttp:durable";
import { call } from "zttp:workflow";

function handler(req: Request): Response & Guarantees {
  const key = req.headers.get("idempotency-key") ?? "demo";
  return run(key, () => {
    const res = call("greet", { method: "GET", path: "/hello" });
    return Response.json({ runKey: key, sub: res.json() });
  });
}

# resolve every call target by name, then serve durably
$ zttp link system.json
$ zttp serve orchestrator.ts --system system.json \
    --durable ./.durable --workflow-queue

You have already met the missing proof. In the playground, the fault-covered chip sits off: a plain handler has no durable recovery path for its effects, so the compiler will not claim one. fault_covered is what durable.run() and proven saga compensates earn.

Hypermedia resources show detail
  • resource(data, affordances) returns one value the runtime renders two ways, chosen by the request's Accept header. You declare what the resource can do once.
  • HAL for services: your data plus _links for navigation and _templates for write actions. HTMX for people: a <dl> of the scalar data, then links and hx-post controls carrying hx-target and hx-swap.
  • An affordance with no method, or with GET or HEAD, is a navigation link. Any other method is a write action. There is no second template to keep in sync.
order.tsone shape, two renderings 
function handler(req: Request): Response {
  const order = { id: 42, total: 1999, status: "pending" };
  return resource(order, {
    self: { href: "/orders/42" },
    pay: { href: "/orders/42/pay", method: "POST", title: "Pay now",
           target: "#order", swap: "outerHTML" },
    cancel: { href: "/orders/42", method: "DELETE" },
  });
}

# same handler, two clients
$ curl -H 'Accept: application/hal+json' localhost:3000/orders/42
$ curl -H 'Accept: text/html' -H 'HX-Request: true' \
    localhost:3000/orders/42
